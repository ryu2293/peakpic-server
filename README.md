## 1. 롤링 배포는 연결을 옮겨주지 않는다

**문제** — 배포할 때마다 연결된 WebSocket이 전부 끊겼습니다. 고치기 전에 먼저 쟀더니,
k6로 세션 40개를 유지한 채 배포하자 전 소켓이 1ms 안에 1006(비정상 절단)으로 동시 종료됐고
서버에는 예외 40건이 남아 있었습니다. Redis 연결 빈이 소켓보다 먼저 파괴되는 종료 순서 결함이었습니다.

**해결** — `SmartLifecycle`로 종료 순서에 끼어들어, 빈이 파괴되기 전에 소켓을 1012로 정리하는
드레인을 구현하고 끊는 시점을 0~3초로 분산했습니다. 클라이언트와는 재연결 계약(종료 코드별 행동,
지수 backoff, 상태 스냅샷 복원)을 문서로 합의했습니다.

**운영에서 한 번 더 틀렸다** — 로컬에선 완성이었지만 운영 배포에선 1012가 0건이었습니다.
끊는 주체가 SIGTERM이 아니라 **ALB 등록 해제(30초)** 였습니다. IMDS의 수명주기 상태를 2초 주기로
폴링해 "종료가 결정된 순간" 드레인하도록 재설계했습니다.

![배포 중 연결 수 그래프](docs/deploy-drain.png)

| | before | after |
|---|---|---|
| 종료 코드 | 1006 × 150 (비정상 절단) | 1012 × 150 (정돈된 종료) |
| 세션 복원 | — | **150/150** |
| 복원 시간 | — | med 0.61s / p95 1.07s |
| 세션 사망 | 전량 | **0** |

## 2. 부하테스트가 찾은 진짜 병목

1 VU가 방장·참여자 소켓 2개를 모두 열어 실제 프로토콜 흐름을 재현하는 k6 시나리오를 설계하고,
페이로드에 전송 시각을 심어 편도 지연을 측정했습니다.

동시 500세션 유지는 여유였지만, **동시 몰림(스파이크)에서는 달랐습니다.**
지표를 분해해 병목을 두 군데에서 찾았습니다:

- 중계 1건당 Redis 순차 **5.3왕복** → Lua 스크립트로 **정확히 1왕복**
  (실측: 중계 48건에 PEXPIRE 146회 → 2회)
- 세션 수립 경로의 **DB 동기 기록** → 비동기 큐로 분리

![k6 before/after](docs/k6-before-after.png)

| 스파이크 p95 | before | Lua 적용 | DB 분리 | 누적 |
|---|---|---|---|---|
| 세션 수립(JOIN) | 408ms | 409ms | 200ms | **-51%** |
| relay SDP | 598ms | 423ms | 212ms | **-65%** |
| relay ICE | 992ms | 656ms | 552ms | **-44%** |

평상 부하는 회귀 없이 유지(4ms → 3ms), 운영 검증에서 중계 유실 0(16,080/16,080)을 확인했습니다.

## 3. 서버가 2대가 되는 순간

소켓은 프로세스에 묶여 있어, 대화 상대가 다른 인스턴스에 붙으면 메시지가 닿지 않았습니다.
**"연결은 로컬에, 이벤트는 공유로"** — Redis Pub/Sub으로 전 인스턴스에 발행하고 소켓을 쥔
인스턴스만 전송하되, 같은 인스턴스면 Pub/Sub을 거치지 않는 로컬 우선 경로를 뒀습니다.

동시성 도구는 상황별로 나눠 썼습니다:
- 스케줄러 중복 실행(2대) → **ShedLock 분산락**
- JOIN 슬롯 경합 → 분산락 대신 **Lua 원자 스크립트** (데이터가 전부 Redis 안이라 1왕복으로 끝남)

경합은 고치기 전에 테스트로 재현해 "naive 방식은 동시 JOIN을 둘 다 성공시킨다"를 문서로 남겼습니다.

## 4. 외부 장애가 전염되지 않게

가짜 침묵 서버로 장애를 주입하자, 카카오와 무관한 게스트 로그인의 최대 응답이 **58.2초**였습니다.
외부 호출에 타임아웃이 없었고, 모놀리스는 톰캣 스레드풀을 전 기능이 공유하기 때문입니다.

**어디에 안 거는가도 설계의 절반이었습니다:**
- 4xx는 서킷 표본에서 제외 — 불량 토큰 폭주로 서킷이 열리면 정상 사용자까지 차단하는 자기 DoS
- 1회성 인가코드는 재시도 금지 — 재시도가 `invalid_grant`를 만듦
- 폴백이 없는 실시간 경로의 DB·Redis에는 서킷 미적용

![장애 주입 실험](docs/outage-experiment.png)

| 무관 API | before | after |
|---|---|---|
| 평균 | 1.00s | **38.5ms** (26×) |
| 최대 | 58.2s | **1.37s** (42×) |

실험에서 가설과 다른 결과도 나왔습니다 — 서킷이 열려 있어도 이미 나간 요청은 스레드를 계속
쥐고 있었습니다. 서킷은 새 호출만 막고, 인질은 타임아웃만이 회수합니다.

## 5. 관측 — 모든 주장의 조준경

Micrometer 커스텀 지표(연결 수·중계 지연·재연결 결과·서킷 상태)를 Prometheus/Grafana로 수집하고,
CloudWatch로 알람을 걸었습니다. 로그는 인스턴스와 함께 사라져 장애 부검을 위해 오토스케일링을
정지시켜야 했던 사고가 있어, **구조화 JSON + MDC(세션·유저 단위 추적) + CloudWatch Logs 중앙화**로
로그의 수명을 인스턴스에서 분리했습니다. 이제 배포로 사라진 인스턴스의 마지막 로그를 쿼리 한 번으로
검색합니다.
